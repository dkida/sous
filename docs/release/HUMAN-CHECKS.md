# Public phone and Natalia checks

Not performed. Use the actual assigned public HTTPS URL after deployment; a
localhost/LAN preview or viewport simulation does not satisfy these checks.

## Phone — exact short checklist

1. Report phone model, OS/version, browser/version and public URL. Open a clean
   private browser session; choose PL. Speak “Mam 200 gramów makaronu, pomidory,
   śmietanę i parmezan.” Allow mic, Stop, review/edit the ingredients, request a
   dish and accept. Report incorrect transcription or unclear proposal text.
2. In cooking, read the entire instruction/quantities and expand ingredients.
   Speak “powtórz”, Stop, and confirm audible speaker output includes useful known
   amounts. Say “Nie mam śmietany” before using it; verify the response/remaining
   plan. Use Done; confirm one step advances. Finish/reset when practical.
3. Type a question with the virtual keyboard open; send it. Scroll to the bottom
   and back, collapse/expand ingredients, rotate the phone if normally used.
   Check mic/send/Stop/Cancel/Done remain reachable above browser chrome/safe
   areas; report any horizontal scroll or hidden controls. Reload retains state.
4. Reset; choose EN. Speak “I have 200 grams of pasta, tomatoes and parmesan.”
   Review/edit and submit. In cooking speak “repeat”; confirm transcription and
   audible useful instruction/quantity. Cancel one recording; typing still works.
5. In a fresh permission-denied session, block the microphone and try mic.
   Confirm a recoverable error and typed proposal/cooking still work. Report actual
   results separately for each browser; restore permission through browser settings.

Return: device/OS/browser; EN/PL transcription and audio pass/fail; keyboard/layout;
reload/reset; denial fallback; approximate longest waits; exact blocking issue.
Do not infer Safari/iOS results from Android or desktop, or vice versa.

## Natalia — minimal handoff

Open the public deployment on her device and say only:

“Powiedz mu, co masz i spróbuj ugotować coś z jego pomocą.”

Observe rather than direct. Prefer real cooking. Let her choose/accept, progress,
ask one voice question and encounter one real unexpected change. If none occurs,
ask her to describe a realistic missing ingredient before using it. Help only if
blocked; record that help. Do not mark a meal cooked if this was only a simulation.

Return concise observations: device/browser, actual meal or simulated session,
where she hesitated/misunderstood, voice errors, whether spoken quantities let her
cook without reading, recipe quality, useful/useless adaptation, unnecessary
phone touches, waits, serious cooking/usability issue and whether she finished.
Record future ideas separately; feature freeze permits only demonstrated bugs,
broken flows, misleading instructions or serious usability fixes.

Results remain pending until the owner reports observations. Then incorporate
those observations (attributed as user-reported) into STATUS.md and verification.
